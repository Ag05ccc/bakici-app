# Node report protocol

The receiver uses only Python's standard library. It stores the latest successful snapshot and latest error for each node/radio in memory. Restarting it reloads configuration and starts with no observations.

Run a development receiver on a free port:

```bash
cp config/server.example.json config/server.local.json
python3 web_app.py --mode server --config config/server.local.json --host 127.0.0.1 --port 8001
```

Example keys are for local demos only. Before deploying, replace each with a distinct value generated by `python3 -c 'import secrets; print(secrets.token_urlsafe(32))'`, and copy only the matching key into that node's agent configuration. Local configuration is ignored by Git. Keep this initial HTTP server on the trusted building LAN.

## Submit a report

Send `POST /api/reports` with `Content-Type: application/json` and `Authorization: Bearer <node-key>`. The request must contain one `Content-Length`, a UTF-8 JSON object, and at most 1 MiB. Chunked transfer is unsupported. Each request reports one completed scan or a heartbeat:

```json
{
  "node_id": "pi-01",
  "kind": "scan",
  "radio": "bluetooth",
  "status": "success",
  "observations": [
    {
      "path": "/demo/bluetooth/device_01",
      "properties": {
        "Name": "Demo beacon",
        "Address": "02:00:00:00:00:01",
        "AddressType": "public",
        "RSSI": -48
      }
    }
  ]
}
```

Wi-Fi uses the same envelope with `"radio": "wifi"` and AP properties such as `BSSID`, `SSID`, `SSIDHex`, `Frequency`, `Channel`, `Strength` (percent), and `Security`. Radio-specific extra properties are retained. Binary values are hexadecimal strings. A successful empty scan sends `"observations": []`.

```json
{"node_id":"pi-01","kind":"scan","radio":"wifi","status":"error","error":"Wi-Fi scan timed out."}
```

```json
{"node_id":"pi-01","kind":"heartbeat","enabled_radios":["bluetooth","wifi"]}
```

Only the documented envelope fields are accepted. Error messages are limited to 500 characters. A successful scan allows up to 1,024 observations with distinct nonempty paths and up to 256 top-level properties each. Nested JSON must be finite and bounded; excessively deep/large values are rejected. Do not include location, IP address, credentials, or timestamps in the payload. Location comes from server configuration; IP comes from the TCP connection; freshness uses server monotonic receipt time.

Responses:

| Status | Meaning |
| --- | --- |
| 200 | Accepted: `{"accepted":true}` |
| 400 | Invalid JSON, report structure, or value/complexity limit |
| 401 | Missing node token |
| 403 | Unknown node or incorrect token |
| 404 | Unknown endpoint, including local scan-control endpoints in server mode |
| 408 | Request body did not arrive before the socket timeout |
| 413 | HTTP request body exceeds 1 MiB |
| 415 | Content type is not JSON |

Rejection leaves existing good state intact. Send reports sequentially for each node/radio, with a 3-second upload timeout. Discard failed uploads and submit a newly completed scan next time; there is no report queue or historical replay.

## Read dashboard state

`GET /api/dashboard` returns `nodes` and `all_observations`. Each node includes ID, label, floor, location, percentage coordinates, source IP, state, last-report age, heartbeat age, and a `radios` object. It never includes API keys.

Each radio contains `state`, `count`, `age` of the last successful scan, `error`, and its last successful `observations`. Fresh empty scans have count `0`. Waiting, disabled, error, stale, and offline results have count `null`; render that as `—`. Retained observations under those states are not current results.

Defaults: nodes become offline at 60 seconds without any report; Bluetooth results become stale at 60 seconds and Wi-Fi at 150 seconds without a successful scan. Errors immediately make retained results unavailable for current counts. Heartbeats and the other radio do not refresh observations. Configurable `freshness` limits use seconds and must stay compatible with agent schedules.

`all_observations.bluetooth` and `.wifi` contain fresh-only groups with an `id` and an `observations` list. Each entry includes its `node_id`, `path`, and `properties`. Bluetooth groups by address/address type, Wi-Fi by BSSID, and missing addresses remain local to a node/path. Signals remain separate for each reporting node.

## Repeat the one-node demonstration

```bash
python3 tools/demo_reports.py --server http://127.0.0.1:8001 --config config/server.local.json --scenario one-node
# Add --auto to send every step without interactive pauses.
```

Inspect `/api/dashboard` after each step: waiting → heartbeat → Bluetooth 2 → Wi-Fi 1 → Bluetooth 0 → Wi-Fi error with a retained stale observation.
